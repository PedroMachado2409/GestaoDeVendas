Anatomia do GestaoPedidos

Um passeio por cada entidade e cada funcionalidade da API — o que o código faz, por que foi feito assim, e o que aconteceria se fosse feito de outro jeito.

.NET 8 · ASP.NET Core EF Core · PostgreSQL Clean Architecture

O mapa

Antes de olhar arquivo nenhum, entenda o desenho. O sistema tem quatro camadas, e a regra que governa tudo é uma só: a dependência sempre aponta para dentro.

WebAPI recebe HTTP, devolve HTTP
Application orquestra o caso de uso
Infrastructure fala com o banco
Domain a regra do negócio

↑ cada camada conhece a de baixo  ·  o Domain não conhece ninguém

O Domain é o centro. Ele não importa Entity Framework, não importa ASP.NET, não sabe que existe HTTP nem banco de dados. É C# puro descrevendo o que é um pedido, o que é um produto e o que pode acontecer com eles.

Por que isso importa

Se um dia você trocar PostgreSQL por SQL Server, ou a API REST por gRPC, o Domain não muda uma linha. A regra de que "não se cancela pedido já finalizado" não tem nada a ver com banco nem com HTTP — e o código reflete isso.

Teste rápido para conferir se a camada está limpa: abra qualquer arquivo em Domain/ e olhe os using. Se aparecer Microsoft.EntityFrameworkCore ou Microsoft.AspNetCore, a camada furou.

Parte 1

O domínio

As entidades. É aqui que vive a regra, e é o que você deve ler primeiro.

A regra comum a todas as entidades

Antes de entrar em cada uma, repare em três padrões que se repetem em todas. Eles não são estilo — cada um resolve um problema.

1. Setter privado

public int Estoque { get; private set; }

Qualquer código pode ler o estoque. Só a própria entidade pode mudar. Isso significa que ninguém escreve produto.Estoque = -5 em algum canto do sistema — a única forma de alterar é chamando um método que valida.

2. Construtor protegido, vazio

protected Produto() { }

public Produto(string nome, string marca, int estoque, decimal preco)
{
    Nome = nome.Trim();
    // ...
}

O vazio existe só para o Entity Framework conseguir montar o objeto ao ler do banco. O protected impede que o seu código o use. Assim, todo produto criado pelo seu código passa obrigatoriamente pelo construtor de verdade.

3. Método com nome de negócio

produto.ReservarQuantidadeVenda(3);   // e não produto.Estoque -= 3;

O nome diz o que aconteceu no mundo real, não o que aconteceu na memória. Quem lê o caso de uso entende a operação sem abrir a entidade.

Prática

Isso se chama entidade rica. O contrário é a entidade anêmica: uma classe só com get; set; públicos, onde a regra fica espalhada pelos serviços. O problema da anêmica é que a mesma regra acaba escrita em três lugares — e um dia divergem.

Cliente

Domain/Entities/Cliente.cs

A entidade mais simples do sistema. Vale como aquecimento, porque mostra um padrão importante: normalizar na entrada.

public Cliente(string nome, string email, string cpf)
{
    Nome = nome.Trim();
    Email = NormalizarEmail(email);
    Cpf = NormalizarCpf(cpf);
    Ativo = true;
    DataCadastro = DateTime.UtcNow;
}

private static string NormalizarEmail(string email)
    => email.Trim().ToLowerInvariant();

private static string NormalizarCpf(string cpf)
    => new(cpf.Where(char.IsDigit).ToArray());

O CPF entra como 123.456.789-01 e é guardado como 12345678901. O e-mail entra como Joao@Gmail.com e vira joao@gmail.com.

Por que isso importa

Existe um índice único de CPF e de e-mail no banco. Sem normalizar, Joao@Gmail.com e joao@gmail.com passariam como dois clientes diferentes — e o índice único não serviria para nada. A normalização é o que faz a restrição do banco significar o que você quer que ela signifique.

Repare também que Ativo e DataCadastro não são parâmetros. Cliente nasce ativo e nasce agora — não faz sentido quem chama decidir isso.

E não existe método Excluir. O sistema inteiro trabalha com Ativar() e Inativar(). Cliente inativo continua existindo, porque os pedidos dele precisam continuar apontando para alguém.

Usuario

Domain/Entities/Usuario.cs

Aqui aparece o primeiro pedaço de segurança de verdade. Olhe este campo:

public Guid VersaoToken { get; private set; } = Guid.NewGuid();

private void RevogarTokens() => VersaoToken = Guid.NewGuid();

E agora olhe quem chama:

public void AlterarSenha(string senhaHash)
{
    Senha = senhaHash;
    RevogarTokens();      // ←
}

public void AlterarRole(UserRole role) { Role = role; RevogarTokens(); }
public void Ativar()   { Ativo = true;  RevogarTokens(); }
public void Inativar() { Ativo = false; RevogarTokens(); }

O VersaoToken é copiado para dentro do JWT quando o usuário faz login. A cada requisição, a API compara o valor que veio no token com o que está no banco. Se forem diferentes, o token é recusado.

O que isso resolve

JWT é, por natureza, impossível de cancelar: uma vez assinado, ele vale até expirar. Se alguém roubasse seu token e você trocasse a senha, o token roubado continuaria funcionando por mais uma hora.

Com o VersaoToken, trocar a senha muda o valor no banco, e todos os tokens emitidos antes deixam de valer no mesmo instante. É o "desconectar de todos os aparelhos" que os aplicativos grandes oferecem.

Prática

Repare que RevogarTokens() é privado e chamado por dentro. Quem troca a senha não precisa lembrar de revogar — é impossível esquecer, porque não há como fazer uma coisa sem a outra. Isso é o que se quer dizer com "a entidade protege o próprio invariante".

Produto

Domain/Entities/Produto.cs

A entidade mais rica do sistema, e a que mais tem para ensinar. Ela controla três quantidades ao mesmo tempo:

CampoSignifica
EstoqueEstá na prateleira, livre para vender
QuantidadeReservadaSaiu da prateleira, separado para um pedido de venda ainda aberto
QuantidadeCompradaPendenteFoi comprado do fornecedor, ainda não chegou

E existem duas trilhas independentes ligando esses campos:

Venda:  Estoque → ReservarQuantidadeVenda → QuantidadeReservada
                → ConfirmarReserva  → (sai do produto, foi vendido)
                → LiberarReserva    → volta para o Estoque

Compra: (fora) → ReservarQuantidadeCompra → QuantidadeCompradaPendente
                → EfetivarCompra          → entra no Estoque
                → CancelarCompraPendente  → some, nunca chegou

A trilha da venda começa tirando do estoque. A trilha da compra não toca no estoque até a mercadoria chegar — porque ela ainda não existe fisicamente.

Armadilha real

Durante o desenvolvimento, o cancelamento de pedido chamava sempre LiberarReserva, sem olhar se era compra ou venda. Cancelar uma compra de 5 unidades adicionava 5 ao estoque — mercadoria que nunca chegou — e ainda consumia reserva de vendas de outros clientes.

A lição: ao criar uma operação nova, procure o par dela. Criou ReservarQuantidadeCompra? Então existe um "desfazer" correspondente. Se você não escreveu, alguém vai desfazer pelo caminho errado.

A validação simétrica

Toda operação passa por uma verificação antes de mexer nos números:

private void ValidarReservaDeVenda(int quantidade)
{
    ValidarQuantidadePositiva(quantidade);

    if (QuantidadeReservada < quantidade)
    {
        throw new ConflictException(ProdutoExceptions.Produto_ReservaInsuficiente);
    }
}

Cada trilha tem a sua validação, com a mesma estrutura. Quando duas coisas fazem o mesmo papel, elas devem se parecer — se uma valida e a outra não, a que não valida é um bug esperando.

O campo Versao

public Guid Versao { get; private set; } = Guid.NewGuid();

private void AtualizarVersao() => Versao = Guid.NewGuid();

Esse campo é chamado de token de concorrência otimista. Ele resolve um problema que só aparece quando duas pessoas usam o sistema ao mesmo tempo.

Imagine a última camiseta em estoque. Dois vendedores abrem a tela ao mesmo tempo, os dois veem "1 disponível", os dois clicam em vender:

  1. Vendedor A lê o produto. Estoque 1, Versao abc.
  2. Vendedor B lê o mesmo produto. Estoque 1, Versao abc.
  3. A grava: UPDATE ... SET Estoque = 0, Versao = 'xyz' WHERE Id = 7 AND Versao = 'abc' — encontra a linha, grava.
  4. B grava o mesmo comando, também com WHERE Versao = 'abc'. Mas a versão agora é xyz. Nenhuma linha é afetada.
  5. O EF percebe que zero linhas mudaram e lança DbUpdateConcurrencyException, que a API traduz em 409.

Sem esse campo, o passo 4 gravaria por cima e você teria vendido a mesma camiseta duas vezes — sem erro nenhum na tela.

Prática

O AtualizarVersao() é chamado em todos os nove métodos que alteram estado. Não em oito. Um método que esquece de atualizar a versão abre um buraco silencioso — e ninguém descobre em teste, porque só aparece com dois usuários simultâneos.

Pedido e PedidoItem

Domain/Entities/Pedidos/Pedido.cs

Esses dois formam o que se chama de agregado: um conjunto de objetos que só faz sentido junto, com uma porta de entrada única.

private readonly List<PedidoItem> _itens = new();
public IReadOnlyCollection<PedidoItem> Itens => _itens.AsReadOnly();

Repare no truque: a lista de verdade é privada. O que sai para fora é uma versão somente leitura. Ninguém de fora consegue fazer pedido.Itens.Add(...) ou .Clear() — porque isso furaria as regras do pedido.

Para mexer nos itens existe um método, e ele começa checando o estado:

public void AtualizarItem(int produtoId, int novaQuantidade)
{
    if (Status != StatusPedido.Aberto)
    {
        throw new BadRequestException(PedidosExceptions.Pedido_NaoPodeSerAlterado);
    }
    // ...
    if (!_itens.Any())
    {
        throw new BadRequestException(PedidosExceptions.Pedido_ItemObrigatório);
    }
}

Duas regras que a entidade garante sozinha: pedido fechado não muda, e pedido nunca fica sem itens.

Os três estados

public enum StatusPedido { Aberto = 0, Finalizado = 1, Cancelado = 2 }

De Aberto se vai para Finalizado ou Cancelado. Desses dois não se sai. Isso se chama estado terminal, e é o que os métodos Finalizar() e Cancelar() protegem.

PedidoItem guarda o preço

public PedidoItem(int produtoId, decimal preco, int quantidade)
public decimal SubTotal => Preco * Quantidade;
Por que copiar o preço

O item guarda o preço praticado no momento da venda, não uma referência ao preço atual do produto. Se o produto subir de R$ 10 para R$ 12 amanhã, o pedido de hoje continua valendo R$ 10.

Sem essa cópia, todo histórico de vendas mudaria retroativamente a cada reajuste — e o faturamento do mês passado mudaria sozinho.

MovimentacaoEstoque

Domain/Entities/MovimentacaoEstoque.cs

Uma entidade com um propósito diferente das outras: ela é trilha de auditoria. Não existe para o sistema funcionar — existe para responder "por que o estoque desse produto está em 3?".

public MovimentacaoEstoque(
    int produtoId,
    string produtoNome,        // ← cópia, não referência
    int quantidade,
    int idOrigem,
    OrigemMovimentacao origemMovimentacao,
    TipoMovimentacao tipoMovimentacao,
    string observacao)

Três decisões para observar:

O nome do produto é copiado. Mesma lógica do preço no item: a trilha precisa dizer como o produto se chamava naquele dia. Se ele for renomeado, o histórico não pode mudar junto.

A origem é um enum, não texto.

public enum OrigemMovimentacao { PedidoDeVenda = 0, PedidoDeCompra = 1 }

Com texto livre, um dia entra "PedidoVenda", outro dia "pedido de venda" — e o relatório que agrupa por origem passa a mentir. Com enum, só existem dois valores possíveis.

Não existe alteração nem exclusão. A interface do repositório tem só duas operações:

public interface IMovimentacaoEstoqueRepository
{
    Task Cadastrar(MovimentacaoEstoque movimentacaoEstoque);
    Task<List<MovimentacaoEstoque>> ListarPorProduto(int produtoId);
}
Prática

Histórico que pode ser apagado deixa de ser histórico. Se um lançamento saiu errado, a correção é uma movimentação nova em sentido contrário — igual a estorno em contabilidade. O erro fica visível, e é isso que se quer.

Parte 2

A aplicação

Os casos de uso. Aqui a regra do domínio é orquestrada em uma operação completa.

O que é um caso de uso aqui

Uma classe, uma operação, um método Executar. O nome é uma frase do negócio: CadastrarPedidoUseCase, FinalizarPedidoUseCase, AlterarRoleUsuarioUseCase.

O caso de uso não contém regra. Ele busca as coisas, chama os métodos das entidades na ordem certa e manda gravar. A regra de "não pode reservar mais do que tem" está no Produto, não aqui.

Detalhe do projeto

Você nunca precisa registrar um caso de uso novo. O Program.cs usa a biblioteca Scrutor para varrer o assembly e registrar automaticamente toda classe terminada em UseCase. Repositórios, ao contrário, são registrados um a um na mão — é a única coisa que exige mexer no Program.cs.

Cadastrar pedido, passo a passo

Application/UseCases/Pedidos/Commands/CadastrarPedidoUseCase.cs

É o caso de uso mais rico do sistema. Vale ler linha por linha.

  1. Abre a transação. Todo o corpo roda dentro de _unitOfWork.ExecutarEmTransacao. Ou tudo acontece, ou nada acontece.
  2. Busca o cliente e recusa se não existir (404) ou se estiver inativo (409).
  3. Descobre quem está vendendo, pelo token — não pelo corpo da requisição.
  4. Busca todos os produtos de uma vez com ObterPorIds, e monta um dicionário.
  5. Para cada item: confere se o produto existe, se está ativo, e reserva a quantidade pela trilha certa (venda ou compra).
  6. Cria o pedido e manda gravar tudo com um único SalvarAlteracoes().

O passo 3 é uma decisão de segurança

var usuario = await _obterUsuarioAutenticado.Executar();
// ...
var pedido = new Pedido(dto.ClienteId, itens, usuario.Id, totalPedido, dto.tipoMovimentacao);

Repare que o CriarPedidoRequestDTO tem apenas ClienteId, Itens e o tipo. Não tem campo de usuário. Isso é proposital.

O que isso evita

Se o identificador do vendedor viesse no corpo do JSON, qualquer vendedor poderia lançar vendas no nome de outro — basta editar a requisição. Como o campo não existe no DTO, mandá-lo simplesmente não tem efeito: o desserializador ignora, e o autor vem sempre da claim do token.

O passo 4 evita o problema N+1

var produtos = await _produtoRepository.ObterPorIds(dto.Itens.Select(i => i.ProdutoId));
var produtosPorId = produtos.ToDictionary(p => p.Id);

Um pedido com 10 itens faz uma consulta ao banco, não dez. Buscar dentro do laço seria o erro clássico chamado N+1: funciona no teste com 2 itens, engasga com 200.

O passo 6 é o coração da transação

Repare que nenhum repositório é mandado salvar durante o laço. As reservas de estoque só mexem nos objetos em memória; o EF anota que mudaram. Só no final:

await _pedidoRepository.Cadastrar(pedido);   // AddAsync, sem salvar
await _unitOfWork.SalvarAlteracoes();        // aqui vai tudo de uma vez

Um pedido com 3 produtos gera 3 UPDATE em Produtos, 1 INSERT em Pedidos e 3 INSERT em PedidoItens — sete escritas, todas juntas. Se a terceira reserva falhar por estoque insuficiente, nenhuma das anteriores é gravada.

O que aconteceria sem isso

Sem transação, os dois primeiros produtos já teriam o estoque baixado quando o terceiro falhasse. Você ficaria com unidades reservadas para um pedido que não existe — estoque sumido, sem nenhum registro explicando para onde foi. E ninguém percebe até a contagem física não bater.

Finalizar e cancelar

Application/UseCases/Pedidos/Commands/

Os dois têm a mesma estrutura, e ensinam um conceito importante: idempotência.

if (pedido.Status == StatusPedido.Cancelado)
{
    return _mapper.Map<PedidoResponseDTO>(pedido);   // sai sem fazer nada
}

if (pedido.Status != StatusPedido.Aberto)
{
    throw new ConflictException(PedidosExceptions.Pedido_NaoPodeCancelar);
}

Cancelar um pedido já cancelado devolve 200, sem erro — e sem mexer no estoque de novo.

Por que isso é desejável

O usuário clica em "cancelar", a internet oscila, ele clica de novo. Sem essa proteção, o segundo clique devolveria o estoque uma segunda vez — criando mercadoria do nada.

Idempotente quer dizer: chamar uma vez ou cinco vezes dá o mesmo resultado final. É uma propriedade que toda operação exposta na rede deveria ter, porque a rede repete requisições sozinha.

Repare que o retorno antecipado vem antes de qualquer alteração de estoque. A ordem das verificações não é detalhe — é o que faz a idempotência funcionar.

A diferença entre os dois

OperaçãoVendaCompra
FinalizarConfirmarReserva — a reserva some, saiu de vezEfetivarCompra — a pendência vira estoque
CancelarLiberarReserva — volta para o estoqueCancelarCompraPendente — some, nunca chegou

O FinalizarPedidoUseCase ainda grava uma MovimentacaoEstoque por item — a trilha só é escrita quando o movimento de fato acontece.

Validação: onde cada coisa mora

O sistema valida em três lugares diferentes, de propósito.

OndeValida o quêExemplo
FluentValidationFormato da requisiçãoQuantidade > 0, e-mail parece e-mail
EntidadeRegra do negócioNão reservar mais do que tem
BancoÚltima linha de defesaCHECK (Estoque >= 0)

Parece redundante. Não é: cada camada protege contra uma coisa diferente. O validador protege contra requisição malformada. A entidade protege contra código errado. O CHECK protege contra qualquer caminho — inclusive um UPDATE manual que alguém rode no banco às três da manhã.

O filtro que amarra tudo

Infrastructure/Filters/FluentValidationFilter.cs

Este arquivo é um dos melhores do projeto. Ele roda antes de cada action, olha cada argumento recebido, procura no contêiner se existe um validador para aquele tipo, e aplica.

var validatorType = typeof(IValidator<>).MakeGenericType(argument.GetType());
if (context.HttpContext.RequestServices.GetService(validatorType)
    is not IValidator validator)
{
    continue;
}

O efeito prático: para validar um DTO novo, você só cria a classe do validador. Não registra, não chama, não altera o controller. O filtro acha sozinho.

Prática

Isso é o que se chama de mecanismo por convenção: em vez de cada desenvolvedor lembrar de chamar a validação, a infraestrutura garante que ela sempre aconteça. Regra que depende de alguém lembrar é regra que um dia falha.

Parte 3

A infraestrutura

O que conversa com o banco e o que trata erro. Chato de escrever, e é o que segura o sistema em pé.

Repositórios

Infrastructure/Repositories/

A regra é simples: repositório lê e escreve, e nada mais. Zero regra de negócio.

public Task<List<Produto>> ObterPorIds(IEnumerable<int> ids)
{
    var idsDistintos = ids.Distinct().ToArray();
    return _context.Produtos
        .Where(p => idsDistintos.Contains(p.Id))
        .ToListAsync();
}

A interface fica no Domain; a implementação, na Infrastructure. É isso que permite ao domínio "pedir" dados sem conhecer Entity Framework — ele conhece só a interface.

AsNoTracking: quando usar

_context.Produtos.AsNoTracking().OrderBy(p => p.Id).ToListAsync();

Por padrão o EF rastreia tudo que você lê, para saber o que mudou na hora de salvar. Isso custa memória e tempo. Em consulta que só vai virar JSON e ir embora, AsNoTracking() pula esse trabalho.

Cuidado

Não use AsNoTracking() em leitura que vai ser seguida de alteração — sem rastreamento, o EF não sabe o que mudou e o SaveChanges não grava nada. É um bug silencioso: nenhum erro, e o dado simplesmente não muda.

UnitOfWork

Infrastructure/Data/UnitOfWork.cs

O arquivo mais sofisticado do projeto. São 30 linhas com três ideias dentro.

public async Task<T> ExecutarEmTransacao<T>(Func<Task<T>> operacao)
{
    if (_context.Database.CurrentTransaction is not null)
    {
        return await operacao();                    // ① já existe transação
    }

    var strategy = _context.Database.CreateExecutionStrategy();   // ②

    return await strategy.ExecuteAsync(async () =>
    {
        await using var transacao = await _context.Database.BeginTransactionAsync();
        try
        {
            var resultado = await operacao();
            await transacao.CommitAsync();
            return resultado;
        }
        catch
        {
            await transacao.RollbackAsync();          // ③
            throw;
        }
    });
}

① A guarda de reentrância. Se já existe transação aberta, ele só executa e devolve, sem abrir outra. PostgreSQL não aninha transações desse jeito — sem essa linha, um caso de uso chamando outro estouraria.

② A estratégia de execução. Existe por causa de uma linha lá no Program.cs: EnableRetryOnFailure(3). Com repetição automática ligada, o EF proíbe transação manual — a não ser que você a embrulhe na estratégia. Quem escreve isso já tomou a exceção e foi entender o motivo.

③ O rollback e o throw. Desfaz e relança. Engolir a exceção aqui esconderia a falha de quem precisa saber dela — o middleware de erro, que vai traduzir em resposta HTTP.

Atomicidade não é concorrência

Confusão comum, então vale separar:

  • Transação resolve "tudo ou nada" — as sete escritas do pedido acontecem juntas ou nenhuma acontece.
  • Token de concorrência (Produto.Versao) resolve "duas pessoas ao mesmo tempo" — impede que uma escrita sobreponha a outra.

São problemas diferentes, com soluções diferentes. Transação sozinha não impede dois vendedores de venderem a última camiseta.

Erros como tipo, não como texto

Domain/Exceptions/ · Infrastructure/Middlewares/ExceptionMiddleware.cs

O domínio não sabe o que é HTTP. Mas ele sabe que "não encontrado" é diferente de "conflito". Isso é expresso com tipos:

AppException
 ├── BadRequestException     → 400
 ├── UnauthorizedException   → 401
 ├── ForbiddenException      → 403
 ├── NotFoundException       → 404
 └── ConflictException       → 409

O caso de uso lança o tipo certo. O ExceptionMiddleware, na borda, traduz em resposta:

var problem = new ProblemDetails
{
    Status = statusCode,
    Title = titulo,
    Detail = detalhe,
    Instance = context.Request.Path
};
problem.Extensions["traceId"] = context.TraceIdentifier;

O formato é o application/problem+json, padronizado na RFC 9457. E o traceId é o detalhe que faz diferença no suporte: o usuário manda o print, você acha exatamente aquela requisição no log.

O middleware também pega o que você não previu

catch (DbUpdateConcurrencyException) { ... 409 ... }
catch (DbUpdateException)            { ... 409 ... }
catch (Exception exception)
{
    var detalhe = _environment.IsDevelopment()
        ? exception.Message
        : "Ocorreu um erro inesperado.";
}
Prática

Em desenvolvimento a mensagem real aparece; em produção, não. Detalhe de exceção conta ao atacante o nome das tabelas, o banco usado, às vezes trechos de consulta. É informação de graça para quem está sondando.

AppDbContext: onde o modelo vira tabela

Infrastructure/Data/AppDbContext.cs

Aqui se declara como cada entidade vira tabela. Três tipos de configuração merecem atenção.

Limites de tamanho

entity.Property(c => c.Nome).HasMaxLength(120);
entity.Property(c => c.Cpf).HasMaxLength(11).IsFixedLength();
entity.Property(p => p.Preco).HasPrecision(18, 2);

Sem HasMaxLength, o texto vira text ilimitado no PostgreSQL. Sem HasPrecision, dinheiro vira um numeric sem escala definida — e dois campos de dinheiro com regras diferentes acabam divergindo no arredondamento.

Índices únicos

entity.HasIndex(c => c.Email).IsUnique();
entity.HasIndex(c => c.Cpf).IsUnique();
entity.HasIndex(i => new { i.PedidoId, i.ProdutoId }).IsUnique();

O último é interessante: garante que o mesmo produto não apareça duas vezes no mesmo pedido. É a mesma regra que o validador do DTO já verifica — só que aqui o banco também garante.

Restrições de verificação

table.HasCheckConstraint("CK_Produtos_Estoque_NaoNegativo", "\"Estoque\" >= 0");
table.HasCheckConstraint("CK_Produtos_Preco_Positivo", "\"Preco\" > 0");
A ideia por trás

A entidade já impede estoque negativo. Então por que o banco também? Porque a entidade só protege o caminho que passa pela aplicação. O CHECK protege contra script de migração, importação de planilha, ajuste manual — qualquer coisa que escreva direto na tabela.

É o princípio de defesa em profundidade: nenhuma camada confia que a de cima fez o trabalho dela.

Migrações

Migrations/

Cada migração é a diferença entre o modelo de ontem e o de hoje, em SQL. O comando dotnet ef migrations add gera o arquivo automaticamente.

O maior aprendizado deste projeto

O arquivo gerado é um rascunho. Quando você adiciona uma coluna obrigatória, o EF gera:

nullable: false,
defaultValue: 0

Todo registro que já existia passa a valer zero. Se a coluna for um valor financeiro, o faturamento histórico inteiro vira zero — sem erro, sem aviso, em silêncio.

E quando você remove uma propriedade da entidade, o EF gera DropColumn. Se a propriedade removida era o token de concorrência, você acabou de desligar a proteção contra venda duplicada — e o único sinal foi uma linha no terminal.

Como uma migração madura se parece

A migração HardeningSegurancaIntegridade, deste projeto, mostra o padrão certo: antes de criar qualquer restrição, ela verifica os dados e se recusa a rodar se algo estiver inconsistente.

IF EXISTS (
    SELECT 1 FROM "Produtos"
    WHERE "Estoque" < 0 OR "QuantidadeReservada" < 0 OR "Preco" <= 0
) THEN
    RAISE EXCEPTION 'Existem produtos com estoque, reserva ou preço inválidos.';
END IF;

A diferença entre uma migração que quebra no meio, deixando o banco pela metade, e uma que para antes de começar e diz o que corrigir.

Rotina que vale adotar
  1. Rodar dotnet ef migrations add
  2. Abrir o arquivo e ler
  3. Procurar por DropColumn e defaultValue
  4. Se houver, escrever o UPDATE que preserva o dado, antes da operação destrutiva
  5. Conferir se o Down realmente desfaz
  6. Só então aplicar

Parte 4

A borda

Onde o HTTP entra e sai. A camada mais fina do sistema, e é assim que deve ser.

Controllers finos

WebAPI/Controllers/

Olhe o tamanho de uma action:

[HttpPost]
public async Task<IActionResult> CadastrarPedido([FromBody] CriarPedidoRequestDTO dto)
{
    var pedido = await _cadastrarPedidoUseCase.Executar(dto);
    return CreatedAtAction(nameof(ObterPorId), new { id = pedido.Id }, pedido);
}

Duas linhas. Sem if, sem try/catch, sem regra. O controller traduz HTTP em chamada e chamada em HTTP — só isso.

O CreatedAtAction é um detalhe correto: devolve 201 com o cabeçalho Location apontando para onde o recurso criado pode ser lido.

Por que manter fino

Regra dentro de controller não pode ser testada sem subir a aplicação inteira. Regra dentro do caso de uso é testável com um objeto e dois mocks. Quanto mais fino o controller, mais do sistema fica testável de forma barata.

Autenticação e autorização

Program.cs · Infrastructure/Security/GerarTokenJwt.cs

O que vai dentro do token

new Claim(ClaimTypes.NameIdentifier, usuario.Id.ToString()),
new Claim(ClaimTypes.Email, usuario.Email),
new Claim(ClaimTypes.Name, usuario.Nome),
new Claim(ClaimTypes.Role, usuario.Role.ToString()),
new Claim("token_version", usuario.VersaoToken.ToString()),
new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())

Note o que não vai: a senha, nem o hash dela. O JWT é assinado, não criptografado — qualquer pessoa lê o conteúdo com um decodificador de base64. Ele garante que ninguém alterou, não que ninguém leu.

A verificação a cada requisição

options.Events = new JwtBearerEvents
{
    OnTokenValidated = async context =>
    {
        var usuario = await repository.ObterPorId(usuarioId);

        if (usuario is null
            || !usuario.Ativo
            || usuario.VersaoToken != versaoToken
            || usuario.Role.ToString() != roleClaim)
        {
            context.Fail("Token revogado.");
        }
    }
};

Depois de conferir a assinatura, o sistema ainda vai ao banco e confere quatro coisas: o usuário existe, está ativo, a versão do token bate, e o papel não mudou.

O custo e o benefício

Isso é uma consulta ao banco por requisição — o oposto do "JWT é sem estado". A troca é consciente: você perde um pouco de desempenho e ganha a capacidade de desligar um acesso na hora. Para um sistema com papéis administrativos, vale.

Fechado por padrão

options.FallbackPolicy = new AuthorizationPolicyBuilder()
    .RequireAuthenticatedUser()
    .Build();

Isso inverte o padrão do ASP.NET: sem essa linha, um endpoint sem [Authorize] fica aberto. Com ela, tudo exige autenticação, e liberar é que precisa ser explícito, com [AllowAnonymous].

Prática

Segurança deve falhar para o lado seguro. Se alguém criar um controller novo e esquecer o [Authorize], o pior que acontece é o endpoint exigir login sem necessidade. Sem o FallbackPolicy, o mesmo esquecimento expõe dado para a internet inteira.

O pipeline, e por que a ordem importa

Program.cs

app.UseMiddleware<ExceptionMiddleware>();   // ① primeiro de todos
app.UseHttpsRedirection();
app.UseCors("Frontend");
app.UseRateLimiter();                       // ② antes de autenticar
app.UseAuthentication();                    // ③ quem é você
app.UseAuthorization();                     // ④ pode fazer isso
app.MapControllers();

Cada requisição atravessa essa fila na ordem. Três decisões dentro dela:

① O tratamento de erro é o primeiro porque ele precisa envolver todos os outros. Exceção que aconteça em qualquer ponto abaixo sobe até ele.

② O rate limit vem antes da autenticação — de propósito. Se viesse depois, um atacante forçaria o servidor a validar milhares de tokens antes de ser barrado.

③ e ④ são coisas diferentes. Autenticação responde "quem é você"; autorização responde "você pode fazer isso". Nessa ordem, sempre — não dá para checar permissão de alguém que você ainda não identificou.

Parte 5

SOLID e KISS, no seu código

Cinco princípios e uma regra de bom senso — cada um com um acerto e uma violação tirados deste repositório.

Antes de tudo: o que isso é

SOLID é uma sigla com cinco princípios de projeto orientado a objetos. Não são leis — são cinco perguntas que valem a pena fazer antes de escrever uma classe.

KISS é Keep It Simple, Stupid: prefira a solução simples enquanto ela resolver o problema.

Como ler esta parte

Não vou te dar exemplos de livro. Cada princípio abaixo tem um trecho do seu código que o respeita e um que o viola. Os dois são úteis — o segundo mais que o primeiro, porque é onde está o aprendizado.

S

Responsabilidade única

Uma classe deve ter um motivo, e só um, para mudar.

Onde você acertou

Application/Validators/Clientes/CpfValidator.cs

public static class CpfValidator
{
    public static bool EhValido(string cpf) { ... }
    private static int CalcularDigito(string numeros, int pesoInicial) { ... }
}

Essa classe valida CPF. Só isso. Se a regra do dígito verificador mudar, ela muda. Nada mais no sistema tem motivo para tocá-la.

Os casos de uso seguem a mesma ideia: CadastrarPedidoUseCase cadastra pedido. Não lista, não cancela. Uma classe, uma operação.

Onde o seu código viola

Infrastructure/Repositories/ProdutoRepository.cs

public async Task Atualizar(Produto produto)
{
    _context.Produtos.Update(produto);
    await _context.SaveChangesAsync();   // ← segunda responsabilidade
}

Esse método faz duas coisas: marca a entidade como alterada — que é trabalho de repositório — e decide gravar no banco — que é trabalho da unidade de trabalho.

Dois motivos para mudar: se o mapeamento mudar, e se a política de transação mudar. Por isso o mesmo projeto tem um UnitOfWork caprichado e três repositórios que o contornam.

Teste prático

Descreva a classe em uma frase. Se você precisar de um "e" no meio — "grava o produto e confirma a transação" —, provavelmente são duas classes.

O

Aberto para extensão, fechado para modificação

Dá para acrescentar comportamento sem editar o que já funciona.

Onde você acertou

Infrastructure/Filters/FluentValidationFilter.cs

var validatorType = typeof(IValidator<>).MakeGenericType(argument.GetType());
if (context.HttpContext.RequestServices.GetService(validatorType)
    is not IValidator validator)
{
    continue;
}

Este é o melhor exemplo do repositório. Para validar um DTO novo você cria uma classe e pronto. Não edita o filtro, não edita o controller, não registra nada.

O filtro está fechado — ninguém precisa abri-lo de novo. E aberto — o comportamento cresce sozinho.

O mesmo vale para os casos de uso: o Program.cs varre o assembly e registra tudo que termina em UseCase. Classe nova entra sem tocar na configuração.

Onde fica pela metade

Infrastructure/Middlewares/ExceptionMiddleware.cs

private static string TituloParaStatus(int statusCode)
    => statusCode switch
    {
        StatusCodes.Status400BadRequest => "Requisição inválida",
        StatusCodes.Status404NotFound   => "Recurso não encontrado",
        _ => "Erro na aplicação"
    };

Criar uma exceção nova derivada de AppException funciona sem tocar no middleware — isso é aberto. Mas se ela usar um status que não está no switch, o título vira o genérico, e aí você precisa editar o método. Fechado pela metade.

Não exagere

Deixar tudo extensível cria abstração demais. A pergunta certa é: "isto vai crescer?" Validadores crescem a cada DTO — vale. Status HTTP são oito e não mudam — o switch está bom.

L

Substituição de Liskov

Onde cabe a classe base, qualquer filha tem que caber, sem surpresa.

Onde você acertou

Domain/Exceptions/ · ExceptionMiddleware.cs

catch (AppException exception)
{
    await EscreverProblema(
        context,
        exception.StatusCode,                    // vem da filha
        TituloParaStatus(exception.StatusCode),
        exception.Message);
}

O middleware captura AppException e nunca pergunta qual é a filha. Não existe if (exception is NotFoundException) em lugar nenhum.

NotFoundException, ConflictException e as outras são intercambiáveis: cada uma entrega o seu StatusCode e a sua mensagem, e o middleware trata todas igual. Isso é Liskov funcionando.

Como seria uma violação

// Se alguém criasse isto:
public class ErroDeIntegracaoException : AppException
{
    public override string Message => throw new NotSupportedException();
}

A classe herda de AppException, então o catch a pega — e o middleware quebra ao ler a mensagem. A filha prometeu ser uma AppException e não cumpriu.

Teste prático

Se o seu código precisa perguntar qual subclasse é para decidir o que fazer, a herança provavelmente está errada. Herança boa é aquela em que você não precisa perguntar.

I

Segregação de interface

Ninguém deve ser obrigado a depender de método que não usa.

Onde você acertou

Repare que este projeto não tem um IRepository<T> genérico. Cada repositório declara só o que os seus consumidores precisam:

InterfaceMétodosTem
IPedidoRepository3Cadastrar, ObterPorId, Atualizar
IProdutoRepository6inclui ObterPorIds e Atualizar em lote
IMovimentacaoEstoqueRepository2só Cadastrar e ListarPorProduto

O da movimentação é o mais interessante. Ele tem dois métodos, porque trilha de auditoria só escreve e lê:

public interface IMovimentacaoEstoqueRepository
{
    Task Cadastrar(MovimentacaoEstoque movimentacaoEstoque);
    Task<List<MovimentacaoEstoque>> ListarPorProduto(int produtoId);
}
O que um genérico teria custado

Com um IRepository<T> trazendo Atualizar e Deletar para todo mundo, a trilha de auditoria ganharia um método de excluir — e a regra de "histórico não se apaga" viraria convenção verbal em vez de garantia do código.

A interface menor não é preguiça. É a regra sendo expressa no tipo.

Onde houve deslize

O IMovimentacaoEstoqueRepository nasceu com um terceiro método, Deletar(int id), que ninguém chamava — e que contradizia o propósito da entidade. Foi removido.

D

Inversão de dependência

Dependa de abstração, não de implementação. E quem manda é a camada de dentro.

Onde você acertou

Repare onde cada arquivo mora — é aí que está o princípio:

Domain/Abstractions/IPedidoRepository.cs          ← o contrato
Infrastructure/Repositories/PedidoRepository.cs   ← a implementação

A interface fica no Domain. Quem define o que um repositório de pedido precisa saber fazer é o domínio, não o Entity Framework. A infraestrutura é que se adapta.

Isso é a "inversão": normalmente o de cima depende do de baixo. Aqui o de baixo depende do contrato que o de cima escreveu.

O mesmo padrão em IPasswordHasher → BCryptPasswordHasher e IToken → GerarTokenJwt. Trocar BCrypt por Argon2 é criar uma classe nova e mudar uma linha do Program.cs.

Onde o seu código viola

Application/UseCases/Pedidos/Commands/CadastrarPedidoUseCase.cs

public CadastrarPedidoUseCase(
    IPedidoRepository pedidoRepository,          // interface ✓
    IProdutoRepository produtoRepository,        // interface ✓
    IClienteRepository clienteRepository,        // interface ✓
    IUnitOfWork unitOfWork,                      // interface ✓
    ObterUsuarioAutenticadoUseCase obterUsuario, // ← classe concreta ✗
    IMapper mapper)

Quatro dependências são interfaces. Uma é classe concreta.

A consequência é bem concreta: não dá para escrever teste desse caso de uso. O Moq só substitui interface ou método virtual, e ObterUsuarioAutenticadoUseCase.Executar() não é nenhum dos dois. É por isso que o caso de uso mais complexo do sistema é justamente o que não tem teste.

O conserto

Extrair uma interface pequena — IUsuarioAutenticado com um método — e injetar ela. Duas linhas de mudança, e o caso de uso vira testável.

Repare como os princípios se cruzam: o teste que falta não é preguiça de testar, é consequência de uma dependência concreta. Violar DIP cobra o preço em testabilidade.

KISS — mantenha simples

Não é "faça código burro". É: não adicione complexidade que o problema não pediu.

O melhor exemplo é uma coisa que foi apagada

Domain/Abstractions/IUseCase.cs — removido

public interface IUseCase { }
public interface IUseCase<TResponse> : IUseCase
{
    Task<TResponse> Execute();
}
public interface IUseCase<TRequest, TResponse> : IUseCase
{
    Task<TResponse> Execute(TRequest request);
}

Três interfaces, com genéricos aninhados. Implementadas por seis classes — todas do módulo Cliente. Os módulos de Produto, Usuário e Pedido ignoravam.

E o que essa abstração comprava? Nada. Ninguém recebia um IUseCase como parâmetro. Ninguém iterava sobre casos de uso. O Scrutor registra por nome de classe, não por interface. Ela foi removida e nada quebrou — a prova de que não fazia falta.

A pergunta que economiza tempo

Antes de criar uma interface, uma classe base ou um genérico: "que código eu consigo escrever com isso que eu não conseguia antes?"

Se a resposta for "nenhum, mas fica mais organizado", provavelmente é complexidade sem retorno.

Outro: capacidade que ninguém pediu

CreateMap<MovimentacaoEstoque, MovimentacaoEstoqueResponseDTO>().ReverseMap();

O .ReverseMap() cria também o caminho DTO → entidade. Ninguém usava. E ele permitia montar uma movimentação a partir de dados de fora, desviando do construtor que valida. Uma capacidade extra que só servia para enfraquecer a entidade.

E o contrário: quando complexidade é necessária

Infrastructure/Data/UnitOfWork.cs

var strategy = _context.Database.CreateExecutionStrategy();
return await strategy.ExecuteAsync(async () => { ... });

Isso não é simples. E está certo assim.

A diferença é que essa complexidade veio do problema, não da sua imaginação: o EnableRetryOnFailure(3) no Program.cs faz o EF proibir transação manual sem a estratégia. Tirar essa linha não simplifica — quebra.

A distinção que importa

Existe complexidade essencial — a que o problema traz — e complexidade acidental — a que você adiciona. KISS ataca a segunda.

O UnitOfWork é essencial: sem ele, transação parcial. O IUseCase era acidental: sem ele, nada muda. Saber separar as duas é mais útil do que decorar a sigla.

Parte 6

Os padrões que atravessam tudo

Se você guardar só cinco coisas desta leitura, que sejam estas.

Os cinco

1 · A dependência aponta para dentro

O Domain não conhece ninguém. A Application conhece o Domain. A Infrastructure implementa interfaces que o Domain declarou. Isso é o que permite testar a regra sem banco, sem HTTP, sem nada.

2 · Regra na entidade, orquestração no caso de uso

Pergunta para se fazer sempre: "isso continuaria verdade se o sistema fosse de papel?" Se sim, é regra de negócio e vai na entidade. Se é sobre buscar, salvar ou coordenar, é orquestração e vai no caso de uso.

"Não se reserva mais do que tem" seria verdade num caderno. Vai no Produto.

3 · Erro é tipo, não texto

Lançar NotFoundException em vez de Exception("não achei") permite que a borda traduza em 404 automaticamente. E permite ao chamador tratar cada caso de forma diferente, sem comparar texto de mensagem.

4 · Defesa em profundidade

Validador, entidade e banco checam coisas parecidas. Não é desperdício — é cada camada não confiando que a de cima fez o trabalho. Quando uma falha, a outra segura.

5 · O que é gerado precisa ser lido

Migração, código de andaime, sugestão de ferramenta. O gerador acerta o caso comum e erra o seu caso específico — e o erro dele costuma ser silencioso. Dois minutos de leitura evitam perda de dado que não tem volta.

Roteiro de leitura

Se você for reler o fonte com calma, esta é uma ordem que funciona — de dentro para fora, do simples para o complexo:
